# SENTINEL X — Development guide

## Prerequisites

- Python 3.10+ (3.12 recommended)
- Node 20+
- Docker (optional — only for the compose stack / cyber range)

## First-time setup

```bash
./scripts/setup.sh        # env, backend venv, db seed, frontend deps
./scripts/dev.sh          # API on :8000, web on :5173
```

Zero-dependency default: **SQLite** at `apps/api/sentinelx.db`. To use
Postgres locally, set `DATABASE_URL=postgresql+psycopg://sentinelx:sentinelx@localhost:5432/sentinelx`
in `.env` (requires `psycopg[binary]`, included in requirements).

## Backend layout

```
apps/api/sentinelx/
  config.py          env-driven settings + startup validation
  db.py              engine / session / init
  models/            SQLAlchemy models (32 tables)
  schemas/           Pydantic schemas (typed API + AI output contracts)
  security/          auth (bcrypt+JWT), rbac, crypto, audit (hash chain)
  services/          scope, policy, jobs, assets, findings, evidence, risk,
                     attack_paths, events, detection, incidents, playbooks,
                     purple, retest, reports, dashboard, exercise, ai/*
  integrations/      ToolAdapter base + adapters (nmap, nuclei, scanners,
                     ingest, lab-range)
  api/               routers + dependencies
  seed.py            demo data (2 orgs, 23 assets/org, findings, incidents…)
  workers/           standalone worker entrypoint
  main.py            FastAPI app, WebSocket hub, in-process worker loop
```

## Frontend layout

```
apps/web/src/
  api/client.ts      fetch wrapper (JWT, tenant, error normalization)
  api/ws.ts          WebSocket client with token refresh on reconnect
  store/auth.ts      zustand auth store (login/logout/me)
  store/live.ts      zustand realtime store (events, incidents, jobs, alerts)
  components/        Layout shell, shared UI primitives
  pages/             one page per module (17 pages)
```

## Everyday workflows

**Add an API endpoint**
1. Model in `models/` (with `org_id` for tenant-owned rows).
2. Pydantic schema in `schemas/`.
3. Service function in `services/`.
4. Router in `api/` with `require_org` + `check_permission`.
5. Re-run migrations + seed for local data.

**Add a tool adapter**
1. Subclass `ToolAdapter` in `integrations/adapters/`.
2. Implement `health_check`, `build_request`, `execute`, `parse_output`,
   `normalize_result`.
3. Return a structured `NOT INSTALLED` result when the binary is missing —
   never crash the platform.
4. Register it in `integrations/__init__.py` (see TOOL-INTEGRATIONS.md).

**Add a migration**

```bash
cd apps/api
./.venv/Scripts/alembic revision --autogenerate -m "describe change"
./.venv/Scripts/alembic upgrade head
```

Every schema change must ship with a migration — `tests/test_migrations.py`
fails CI when the migration tree drifts from the SQLAlchemy models. Note:
SQLite cannot detect `nullable` changes via autogenerate; write those by hand
(see `alembic/versions/a1b2c3d4e5f6_login_hardening.py`).

## Tests

```bash
./scripts/test.sh
# or: cd apps/api && ENVIRONMENT=test python -m pytest ../tests -q
```

The unit suite covers: auth + RBAC + login lockout, scope/policy rejection
paths, full offensive → defensive → purple workflows, job lifecycle, tenant
isolation, AI schema validation, and migration discipline. Tests run against
an isolated SQLite DB created per session.

### Full security lifecycle acceptance test

The definitive "the whole project works" test drives the complete authorized
loop against the LIVE lab: engagement → real DAST scan → real findings →
validation → evidence → attack path → controlled attack → live telemetry →
detection → incident → AI analysis → approved response → **measured real
state change** → remediation → **real retest (PASS)** → regression check
(FAIL) → report. It skips cleanly when the API/lab are not running.

```bash
# start the lab targets locally (no Docker needed):
./scripts/lab.sh

# run the acceptance test:
ENVIRONMENT=development API_URL=http://127.0.0.1:8000/api \
  LAB_WEB_URL=http://127.0.0.1:5000 LAB_API_URL=http://127.0.0.1:9002 \
  python -m pytest tests/test_complete_lifecycle.py -q
```

## Code style

- Type hints everywhere; Python `from __future__ import annotations`.
- SQLAlchemy 2.0 typed `Mapped[...]` style.
- No fake data in production paths — demo artifacts are generated by
  `services/exercise.py` and always labeled `CONTROLLED LAB`.
- Errors: structured `detail` messages; failed jobs record the error and
  never flip to `completed`.
